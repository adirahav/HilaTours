# Plan: Signup page

Status: done
Owner: Orchestrator
Last updated: 2026-08-10
Scope-Agents: frontend, user-management-service, qa, security

## Goal
Add a standalone Admin Sign Up page (`יצירת חשבון חדש`) at `frontend/src/pages/SignUpPage.tsx`, wired to the existing `POST /api/auth/signup` endpoint, matching the design in `raw_from_ai_studio/src/pages/SignUpPage.tsx` and PRD Screen 2 / F1b.

## Scope
- In scope:
  - New `frontend/src/pages/SignUpPage.tsx` (fullname/email/password form, show/hide password toggle, client-side validation, RTL Hebrew copy) plus a route for it (e.g. `/signup`).
  - `frontend/src/services/auth.service.ts`: add a `signup()` method calling `POST /auth/signup` on `userManagementClient`.
  - Links from the new page: "יש לך כבר חשבון? התחבר" → `/login`, "חזרה לעמוד הראשי" → `/` (Gateway).
  - A link/entry point from the existing Gateway/login flow to `/signup` (PRD says it's a separate page, not a Gateway modal).
  - Verifying/hardening `backend/user-management-service` so that self-signup never yields admin permissions (see Risks — the current `Admin` model has no `roles`/permission concept at all, so this needs confirmation or a fix, not just a UI wrapper).
- Out of scope: any change to bus/tour/seat flows, forgot-password flow, email verification.

## Assumptions
- Design source: `raw_from_ai_studio/src/pages/SignUpPage.tsx` (fields, copy, layout, validation rules: name ≥2 chars, email regex, password ≥6 chars) — directly usable as the visual/behavioral reference.
- Backend route `POST /api/auth/signup` already exists (`backend/user-management-service/api/auth/auth.controller.ts` + `auth.service.ts`) and accepts `{ fullname, email, password }`, returning a JWT — matches `SignupData` in the user-management-service API contract.
- Existing `frontend/src/components/common/GatewayAdminLogin.tsx` and `frontend/src/pages/LoginPage.tsx` establish the pattern (page wraps a form component, uses `authService`, `useStore`) that `SignUpPage` should follow.
- Successful signup should not auto-login the user into an admin session; it should route to `/login` per the raw design's `onGoToLogin` behavior (PRD explicitly says signup grants no admin permissions).

## Open Questions
- Should a successful signup auto-log the user in (store JWT, redirect to `/admin`) or only redirect to `/login` for the user to authenticate separately?
   - Recommended: redirect to `/login` only, do not auto-store the token — matches the raw design (`onGoToLogin`) and avoids implying the new account has admin access it doesn't have.
   - *HUMAN ANSWER:* redirect to `/GatewayAdminLogin`
- Where should the entry point to `/signup` live (Gateway page footer link, LoginPage footer link, or both)?
   - Recommended: add it to `LoginPage`/`GatewayAdminLogin` footer only (mirrors the raw design's `onGoToLogin` counterpart link), since Gateway's primary choice is passenger-vs-admin-login, not signup.
   - *HUMAN ANSWER:* add it to `LoginPage`
- Should the plan also fix the backend so self-signup can never carry admin permissions, given `Admin` model currently has no `roles` field at all (see Risks)?
   - Recommended: yes — add a `roles: string[]` field (default `["user"]`) to the `Admin` model/schema in this same task and gate all admin-mutation routes on it, since shipping the signup UI without this makes every self-registered account indistinguishable from a real admin today.
   - *HUMAN ANSWER:* yes

## Steps
1. `frontend` agent:
   - Build `frontend/src/pages/SignUpPage.tsx` per the raw design (fields: full name, email, password w/ show-hide, submit "הרשמה למערכת", links back to login/gateway), using existing form patterns from `frontend/src/components/common/GatewayAdminLogin.tsx`.
   - Add `signup()` to `frontend/src/services/auth.service.ts` (`POST /auth/signup` via `userManagementClient`), returning/ignoring the token per the Open Questions answer (no auto-store).
   - Add `/signup` route in `frontend/src/App.tsx` and a link to it from `frontend/src/pages/LoginPage.tsx` (or `GatewayAdminLogin`).
   - Add `frontend/src/pages/SignUpPage.test.tsx` covering validation states, submit success/error, and navigation links.
2. `user-management-service` agent (parallel with step 1, independent):
   - Add `roles: string[]` (default `["user"]`) to `backend/user-management-service/api/models/admin.model.ts`; ensure `signup()` in `auth.service.ts` always sets `roles: ["user"]` regardless of request body input (reject/ignore any client-supplied `roles`).
   - Confirm/add `requireAdmin`-style middleware checks so any existing admin-only route actually checks `roles.includes('admin')` rather than "is authenticated" alone; add/adjust tests in `backend/user-management-service/api/auth/auth.test.ts`.
3. `qa` agent runs frontend and user-management-service test suites plus a signup→login manual-flow smoke check.
4. `security` agent audits the new signup page and backend role enforcement (privilege-escalation via signup body, JWT claims, no admin auto-grant).

## Validation
- frontend: npm --prefix frontend run lint && npm --prefix frontend run build && npm --prefix frontend run test
- backend/user-management-service: npm --prefix backend/user-management-service run test

## Risks
- **Privilege model gap (user-management-service):** the `Admin` Mongoose model has no `roles`/permission field today — every account created via `signup()` (or `login()`) is structurally identical to an "admin" account. Shipping a public signup page on top of this means any visitor can create an account that is, in practice, indistinguishable from an admin unless this is fixed. This must be addressed in the same task, not deferred, per planning-rules guidance on not excluding a backend service when Risks flags it.
- Client-supplied `roles` (or similar) in the signup request body could attempt privilege escalation if the backend ever naively spreads `req.body` into `Admin.create` — must be explicitly ignored/overwritten server-side.
- UX risk: without clear messaging, users may believe signup grants admin/management access; the success message and footer copy must not imply this (PRD requirement).

## Rollout Order
1. Backend (user-management-service) roles field + enforcement.
2. Frontend SignUpPage + route + auth.service signup().
3. QA verification.
4. Security audit.
